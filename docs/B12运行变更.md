# B12 运行变更（2026-09-22）

本页在 B12 部署后适用，结合程序根目录的《运行交接-给其他Agent.md》和当前 `config.json` 使用。

## 当前生产范围

`initialize.seed_stage=false` 继续保留：初始化不会生成 seed，也不会消费 quicknote/inbox。不要为了追求吞吐修改扫描范围、清空 processed 或批准旧队列。存量卡片修复、全库重跑和 seed 重新启用均不属于本次升级。

## 混合批次如何处理

- 正常 LLM 源页进入原有 plan → 逐页 review → apply 流程，人工审核仍然必要。
- 非 LLM / heuristic-fallback 源页不再进入可写页面集合。计划的 source 阶段 `input_outcomes` 保留 `blocked`、`complete=false`、`analysis_mode`、原失败原因和 `non_llm_source` 说明；它不是已处理成功，也不是人工拒绝。
- 下次初始化优先处理首次待生成资料，再尝试失败资料。失败诊断仍在计划和 receipt 中，不需要删除原始输入或伪造完成记录。
- `--no-llm` 可用于离线诊断，但不会产生可写的源卡。旧计划中的非 LLM 页面仍会被严格预检拒绝；请按新的程序重新生成计划，不手改旧 plan 的模式或 hash。
- 审核和诊断都按完整 `run_id` 查看。批准正常页时仍要处理同一运行的必要诊断项；不要全队列批量批准，也不要把批准诊断理解成批准失败页写入。

## 模型调用与等待

新增可选 `llm` 设置，无需在活配置中添加也会使用默认值：

```json
{
  "max_attempts": 3,
  "retry_backoff_seconds": 1,
  "retry_budget_seconds": 300
}
```

`max_attempts` 包含首次请求。仅对明确瞬时错误（408、429、500、502、503、504、超时与部分连接错误）重试；认证/请求错误、坏 JSON、非法响应和内容安全失败不重试。不改变现有模型、请求格式或提示词。

原 `timeout_seconds` 继续限制单次 socket 操作；剩余重试预算同时限制下一次调用的 timeout 和等待时间。**这不是整个批次的强制墙钟截止**，也不是对 provider 延迟改善的保证。长资料有多次分块调用；外层运行时限应结合批大小设置，不能把进程超时当成功。

## 初始化声明与审核记录

初始化声明从 `workflows.json → entries.init_kb.pipeline` 读取。支持固定顺序：`intake → source_compile → seed_cluster → promote_candidates → quality_gate`；可以省略 seed、promote 两个可选阶段，必需阶段缺失、未知/重复/乱序声明会明确报错。不是任意步骤编排器。`initialize.seed_stage=false` 始终覆盖 pipeline 中的 seed 开启声明。

运行 `scripts/validate_config.py` 检查配置。禁用阶段会记录原因及零调用，不会伪装成执行成功。

审核摘要显示 pending、approved、applied、rejected；applied 表示已核验写入，与“已批准但未写入”分开。新队列时间明确使用 UTC（`+00:00`）。历史无时区队列时间仍按旧代码的 UTC 理解；旧 manifest 的本机时间可能相差 8 小时，核对时以 `run_id`、目标和实际写入证据为准，不改写历史记录。

## 仍然需要人工判断的部分

编码图片链接和机器片段会从启发式信息单元中排除，标题后正文恢复提取；引用坐标仍绑定原文。这不证明信息为真，也不使启发式卡片获得写入资格。seed 的“单个想法发芽”、关系质量与历史内容复审继续作为后续质量工作，先验收少量样张再启用。
