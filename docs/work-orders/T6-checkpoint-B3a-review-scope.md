# B3a — pure page review scope helper (preparation only)

NOT DISPATCHED. This independent foundation can run alongside B1b/B2; production subset apply wiring waits B2. Own NEW core/page_review_scope.py and tests/test_page_review_scope.py, plus B3a report only. No changes to CLI/review_runs/review_queue/state/pipeline while integrator owns those. Public/synthetic only, no model/network/private data/commits/subagents. Preserve others.

Create a pure helper with two exported interfaces:
- page_review_records(plan) -> list[dict]: for ALREADY object-bound saved-plan pages, build versioned `type=planned_page_review`, scope='page', exact run_id, canonical target, operation, object_id/revision/base revision if applicable, content_sha256 recalculated and verified. Never use filename/title alone. Stable review key derived from run+target+content hash, but queue UUID remains queue module authority. Reject duplicate/conflicting targets, malformed hash, content/declared-hash mismatch, unknown operation. No writes or new object IDs.
- select_page_review(plan, queue_items) -> a structured selection of original page objects, authorized target/hash map, selected review IDs, pending/rejected/applied targets, run blockers and explicit conflicts. Only the EXACT run+target+content-hash scoped record can authorize a page. Unknown/stale/duplicate conflicting records fail closed. Approved one page never authorizes another. Existing non-page run records remain blockers unless approved/applied. Legacy aggregate `planned_pages_require_review` is not page authority and cannot silently become it. Old run-only plans may stay on existing whole-run path until regenerated; report this honestly.

No arbitrary approval helper, no page/content mutation, no actual writing. Parse links using existing vault link semantics if available: selected output that would link a future pending/rejected sibling page must produce a visible dependency blocker; already applied sibling may be allowed only with actual output verification supplied by integrator, not queue status alone. Prefer accept an explicit `applied_outputs` mapping validated by outer caller as optional argument rather than performing filesystem reads. Defaults trust nothing. Define that mapping contract precisely.

Tests: bound multi-page synthetic plan, one approved+pending/rejected, all approved, non-page blocker, forged run/target/hash, content changed after review, duplicate scope records, one-page approval cannot grant aggregate authority, already-applied mismatch/default-no-trust, future sibling link. Do not alter production wiring; provide exact integration contract in docs/iteration-evidence/M3-integration/checkpoint-B3a.md/json. Root review then B3 writer integration by original integrator.
