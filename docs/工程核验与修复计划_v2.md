### 附件自身的证据质量检查

这些结论只针对反馈文档，不冒充对真实知识库的复跑。

**A. 评论标题计数错误。** 附件 L231 写“评论（16 条）”，该 issue 的正文元数据 L27 写评论数3，实际存在3个 `#### 评论 ·` 块（L233/L322/L385）。L1188 写“评论（25 条）”，元数据 L1092 写评论数2，实际存在2个评论块（L1190/L1254）。计数规则、章节边界及结果均由 `audit_feedback_manifest.py` 输出。它不意味着缺少其余评论，也不能拿16与25当评论数量。

**B. 宿主删除额度作用域没有可靠统一口径。** #16 早期评论 L317–319 声称按进程计数、重启进程可续跑；#18 L471–490 却称 `scope=turn`，拆进程无效。两者是前后报告，不当成同一次运行。现缺宿主版本、策略、完整错误与驱动记录，不能选择一种解释当作已复现根因。提高探测效率依然值得做，但“长批次必然卡死”的泛化不成立。

### 决定性反例与报数口径

**围栏反例。** 在临时文件中放入同一条仿真命令：仅放在正常反引号围栏内时，原函数返回空；同时放在围栏外时，只保留外部摘录。命令为 `--case signal`，经实际 `read_note` 读入后调用 `signal_sentences(limit=2)`。这反驳的是原报告的字符串归因，不是说明所有 Markdown 围栏都解析正确。

**新的独立围栏缺陷。** 四个反引号开启的文本块中出现三个波浪号时，布尔开关被错误翻转，内部 `DEMO_ONLY_VALUE_123` 被抽出。CommonMark 要求闭合围栏与开启围栏字符一致，且长度不短于开启围栏；现实现没有保存这两项状态。本夹具不含真实秘密、不调用外部模型。

**渲染反例。** `--case render` 使用同一份包含 summary、key_facts、topics、quality_flags、analysis_mode 的合成输入，仅切换 Jinja 导入成功/抛 ImportError。输出正文中 `line.startswith('## ')` 的计数分别为 **5 / 0**；渲染调用捕获的 warning 为 **0**。正常启发式页被原门禁拦截，降级页未被拦截，原因是门禁看正文词句而非 page 的 analysis_mode。此数不是用户的 sources 目录统计。

**候选页反例。** `--case promotion` 只取同一组三个标记命中的临时 raw 文件。规则 min_sources=3、max_sources=8：整组调用原 promoter 得到 **1** 个待审核候选；拆成单文件批次，得到 **[0,0,0]**；不配置规则得到 **0**。这是批次依赖，不是满足条件后仍无法产出。将 max_sources 改为2、min_sources 保持3，现配置校验也不报错。

**探针口径。** `--case probe` 对 **100 个不存在的目标文件、同一个已存在父目录**调用原 preflight，按 `.write-check-` 前缀记录原 Path.write_text/unlink 调用，各 **100 次**；业务页写入 **0**。这些不是完整 apply 的总删除次数。删除 PermissionError 与 SystemExit 是不同注入分支，不是还原原宿主。

**PR 坏夹具口径。** `--case fixture` 对固定 main 的 `examples/mini-vault/raw/industry_report.md` 全部原始字节运行 `len(bytes)` 与 `bytes.count(bytes.fromhex('efbfbd'))`，结果为 **255 字节、35 个 EF BF BD 序列**，与 PR 相符。原 read_note 读入后仍带 U+FFFD。这里能确认数据含损坏痕迹，不能从现存字节唯一复原最初编码历史或被替换的中文；两种 UTF-16 token 子串检验都命中，不能仅据此断言唯一 BE 编码。

**链接口径。** `--case seed` 的两个来源来自 quicknote/a.md 与 quicknote/b.md；原 renderer 的来源区和摘录归属均含真实 wikilink。`--case updates` 则构造既有相近标题 seed，执行原 prepare_seed_updates，最终 related 非空。原私库“相关链接小节为空”的统计不能替代“整张卡没有任何出链”。

## 第二部分 · 根因归并

### G1 · 渲染契约失守，而非模型不会提取

**节点：** `core/jinja_renderer.py:50–72`；`skills/topic-research-compile/renderer.py:34–55`；CLI 的正文字符串门禁。**归属：#27，PR #28 的内容契约部分。**

数据流：结构化提取结果 → 静默摘要 fallback → 高置信度/免审核外层元数据 → 正文缺少降级标记 → 被当成普通 source-note。原函数对同一输入的差异已经复现。

下游症状：关键事实、专题边界与质量标记未进入 Markdown；`core/finalizer.py:77–90,248` 按正文小节读取事实/专题，其输入因此缺失；来源处理成功记录还会阻止无源码变化时的自动重跑。

**不修的最坏后果：** 每篇受影响的派生来源页只保留摘要，质量警告也消失；补装依赖后，仅再次增量运行不能保证修补历史页。原 raw 未被该机制删除，但丢失的 LLM 提取结果若未另存，只能重新生成，不是补几个标题就能恢复。

不能与 #22 全部合并：初始化 promoter 直接看 current_raw_batch，不靠这些小节；只有后续 finalizer 消费 source-note 时才受此根因牵连。

### G2 · seed 生成器的扩展信息没有实现；并非没有任何链接机制

**节点：** `core/seed_quality.py:71–74`；`core/seed_updates.py:30–38`。**归属：#23、#26 的固定文案/普通关联部分、#21 的阶段文案部分。**

下游症状：summary 使用聚类 reasoning；growth_directions 为通用文案；普通知识关联没有候选检索与证据判断。已有后处理仅按标题处理疑似重复，它不能代替跨主题知识关联。

**不修的最坏后果：** 使用者得到可追溯的分类提案，却仍需手工判断每张卡的下一步与跨域关联。不能据此推导材料检索全面不可用，更不能升级为 P0。

#26 的原子卡/聚合卡取舍不纳入本根因；聚合器同样可以生成关联，原子卡同样可以硬编码空关联，二者不存在必然因果。但现有规格并不能证明用户的新产品诉求没有价值：单输入能产卡不等于有聚焦发芽能力，思想内核、具体生长方向和跨域关联应作为单独能力验收。

### G3 · 摘录类型与证据资格未分离；围栏状态机另有独立缺陷

**节点 A：** `core/seed_quality.py:14–37,45–49` 的结构摘录；**归属：#24、#25 更正后裸行问题、#26 信号定位部分。**

结构过滤只证明某段文字被读到，既不证明它是断言，也不证明它支持聚类主题。裸操作记录、链接资料、问题、断言应分型；不能一律改写成肯定事实。`core/clustering.py:99–106` 的 terms 主要从标题切分，也不等同于独立概念抽取。原私库关键词空白分布仍未复现。

**节点 B：** `core/seed_quality.py:20–21` 只翻转布尔量，不记录围栏字符及长度；这是第一轮独立复现的解析缺陷，不是原报告中内外同字符串的错判。

**不修的最坏后果：** 不具备证据资格的摘录被后续当成支持材料；应留在代码区的文本在特定围栏布局中进入摘录。当前函数不拦截仿真凭据形态，故秘密过滤需在外发模型前另设边界。第一轮没有证实任何真实凭据外泄。

### G4 · 生产者、skill schema、状态文档不在同一契约上

**节点：** `core/seed_quality.py:69` 对比 `skills/mindseed-grow/schema.json:16`；`core/skill_executor.py:36–44`；`core/skill_runtime.py:87–94`。**归属：PR #28；与 #16 的状态变更相接。**

下游症状：正常生成的 candidate seed 被其自身 JSON schema 判为非法；现 runtime 的通用类型/来源/链接校验没有替代完整的按 skill schema 校验。不能说“无校验”，也不能只改 enum 让一切通过。

**不修的最坏后果：** 新消费者按 schema 拒收当前合法业务流程产物；不同入口对同一状态给出不同答案，历史迁移无法可靠区分坏状态与文档落后。

损坏夹具读取不告警是相关的“输入契约”问题，但不是 stage enum 漂移造成的，需独立子任务。

### G5 · 候选提升只看当前批、配置约束不全、阶段记录不完整

**节点：** `core/initializer.py:126–169` 及 make_initialization_plan 的 current_raw_batch 调用；`workflows.json:15–23`。**归属：#22。**

下游症状：相同材料采用不同分批方式，候选产物不同；无配置和命中不足都返回空，promoter 计划记录缺少明确的零产出原因；max_sources/min_sources 不可满足组合也被接受。

**不修的最坏后果：** 即使整个库已经有足量同主题来源，初始化仍持续不产出候选，调用者无法区分未配置、未匹配和确实失败。

现有 `core/finalizer.py:248` 已做跨 source-note 聚合，不能重复建设成另一条无关跨批系统。seed 提升要另定义证据资格，不能把 seed_terms 计数当作知识成熟度。

### G6 · 执行边界的三个独立根因，不能因为都在 Windows 使用时暴露就合成一个

**G6a / #18：** CLI `:1286–1298` 按目标文件重复探测父目录，清理失败被吞。后果是在具有操作额度的宿主中消耗不必要的删除操作，或积累未报告的探针。是否中止由真实异常类型决定。

**G6b / #20、#21 部分：** CLI `command_review` 选取全部 approved runs，没有单 run apply 入口；暂停说明与实际阻塞条件不一致；`record_failed_attempt` 的输出未结构化异常类型和部分写入决策。后果是操作范围不清，恢复时做出错误动作。现有 run 保护不是缺陷，不应删除。

**G6c / #19：** 路径防护在原生 Windows 的疑似失败。尚未证实，不能归为 G6a 的宿主删除守卫，也不能先交付只检查 is_symlink 的替代方案。普通 symlink、junction、重解析点与检查后替换不是同一测试条件。

### G7 · 修算法不等于修存量：processed 只看来源版本

**节点：** `core/state.py:80–91`；`core/seed_updates.py:45–52`。**归属：#16 评论的旧卡未更新；与 #27 历史残缺来源页相交。**

下游症状：原文 hash 不变、处理状态为 created/skipped 时，旧生成器处理过的内容仍被当作已完成。

**不修的最坏后果：** 新程序已经正确，历史产物长期保持旧质量；若操作者反过来清空 processed-index 强制重跑，又会制造重复提案或误触人工页。应建立显式、可审核的版本迁移，而非偷偷覆盖旧卡。

### 批次 B · 确立机器可检查的输入/产物契约

**涉及文件：** `skills/*/schema.json`、`core/skill_executor.py`、`core/skill_runtime.py`、`core/json_contract.py`、`core/validator.py`、`core/vault.py`、source renderer、CLI page gate、状态文档、requirements（仅选用 JSON Schema 校验器时新增运行依赖）。

**改动要点：**

1. 定义每类产物自己的 status/stage 组合。seed 当前可保留 `status=seed|manual_review` 与 `stage=candidate|needs_context`；legacy seed 是否接受由迁移契约显式规定。不能把所有历史值塞入同一宽松 enum。
2. 在 structured item → renderer 前执行按 skill 的 schema 校验；不要直接把结构化 item schema 套到 `created/pages` 执行器信封上。来源路径、已知链接和对象 identity 校验继续保留。
3. source-note 增加明确 schema、正文规格与 `analysis_mode/render_mode/quality_flags` 等结构化质量字段；门禁不再 grep 自然语言文案。source-note 单来源合法，研究结论的证据充分性另检。
4. 输入解码错误、已有 U+FFFD/NUL 等异常记录为可审核的数据质量问题，不自动复原原文，不一律禁止文件中的合法替换符。对已确认损坏夹具，不让模型凭残片完成未受证据支持的摘要。
5. 文档区分 `writes_by_default`、`conditional_outputs`、`follow_up_outputs`。topic-research 当前 executor 只产 source-note；不为凑声明强制每篇制造 topic/concept/evidence 页。
6. 在产物中记录生成器版本与来源 hash，为 F 建立选择依据；暂不触发旧库重写。

**验收：** 新增 `tests/test_output_contracts.py`、`tests/test_source_quality_contract.py`，执行 `python -m pytest -q` 对这些文件。所有正常 fixture 的 structured item 均通过对应 schema；注入非法 stage 必须在渲染前失败；heuristic/quality_flags 门禁不受正文措辞修改影响；坏夹具不得被默默当成可用原文；正常 UTF-8、BOM、CRLF 与合法稀疏来源页不被误拒。

**回归风险：** 一上来启用旧 schema 会拒绝当前 candidate；布尔值读取与旧 YAML 格式不一致；把空 related 改成不合法会逼模型造链接。必须先对齐 schema，再打开强校验。

### 批次 C · 让执行范围、探测与失败恢复可控

**涉及文件：** `scripts/personal_kb_steward.py`、`core/review_queue.py`、`core/run_records.py`、`core/output_paths.py`、`core/safety.py`、CLI 文档、Windows 测试。

**改动要点：**

1. 为 `review apply-approved` 增加 `--run-id`；全局执行使用显式 `--all` 或清晰的兼容期提示。暂停和 apply 复用同一 run 阻塞判定，输出阻塞项 ID/type/reason。
2. 每个 run 单独输出选中计划、成功/失败、create/update/已验证写入数，并及时持久化审核状态；不能等后面 run 失败后丢失前面的审核状态更新。
3. 错误事件记录 `exception_type/message/cause/context/phase/run_id/created_count/write_started/recovery_mode`；stderr 不只给退出码。日志中的敏感内容需脱敏。
4. 在一次 apply 的 preflight 中按实际父目录去重探针；若宿主禁止清理，明确告警或采用经过设计的宿主模式。每次执行仍需重新判断，不能看历史固定文件存在就认定今天可写。
5. 对 #19 先增加原生 Windows 3.12/3.13 的真实目录 symlink 与 junction 测试，包括库内 raw、库外目录和未存在目标。无权限 skip 不能算通过。只有复现后才实施对应补强；保留 realpath containment，不用单独 is_symlink 替代全部路径约束。
6. 部分失败保留现有 run manifest 不可覆盖规则。包含 update 的 run 不允许被 delete-only rollback 删除。此批不引入按 issue type 批量自动批准质量问题。

**验收：** 新增 `tests/test_review_run_scope.py`、`tests/test_preflight_probe_policy.py`、`tests/test_failure_diagnostics.py`。队列夹具含 run-a/run-b/run-c，指定a时b/c不变；c的阻塞项必须给ID而非仅数量。同一已存在目录的100个拟新建页，探针策略只执行一次该目录探测；**不是要求全流程零删除**。注入写入中断后 manifest 保留真实已写页，既不谎称完整成功，也不提示无条件原样重跑。#19 另执行仓库现有的 symlink 用例并保存实际 Windows 输出。

**回归风险：** 改全局 CLI 默认会影响驱动脚本；逐目录缓存若跨 run 存活会掩盖权限变化；仅符号链接检查遗漏其他路径类型；捕获异常时不可吞掉取消或中断而继续写入。

### 批次 D · 改进可生长信息，但保留摘录与判断的界限

**涉及文件：** `core/seed_quality.py`、`core/clustering.py`、`core/seed_updates.py`、seed executor/renderer/schema、检索与链接验证层；新增有界的信号分类/secret-screening 模块。

**改动要点：**

1. 围栏状态保存 marker 字符与长度，按 Markdown 规则开闭；内部保留来源行范围。raw quote 与展示文本分开，不用整文件字符串搜索推断摘录位置。
2. 增加 signal kind，例如 assertion/question/procedure/reference。只有具备支持关系的 assertion 才进入证据池；短问题、命令和链接不按长度或首词一刀切抹除。
3. 模型提炼的 statement 必须带 exact quote、source、source hash、span。改写结论不替换原文依据，不把聚类高置信度解释为事实已验证。

**验收：** 新增 `tests/test_seed_signal_contract.py`、`tests/test_seed_growth_links.py`。同文内外重复摘录定位到外部行；异种/不同长度围栏夹具不泄出内部哨兵；短但完整的合成断言、问题与程序片段分型保留；仿真凭据不进入捕获的模型 payload 或日志。相关链接全部从已知集合解析，无匹配时输出明确空结果；候选/需补上下文的动作不同。全部不读取真实私库、不使用真实秘密。

**回归风险：** 秘密筛查误杀正常技术内容；语义改写制造新事实；要求每卡有链接导致伪关联；改变信号格式破坏现有 renderer。通过 B 的版本化 schema 过渡，保留人工审核。

### 批次 E · 跨批提升与真实阶段账本

**涉及文件：** `core/initializer.py`、`core/finalizer.py`、`core/layout.py`、workflows/config 文档与相关契约测试。

**改动要点：** 拒绝 max_sources < min_sources 等不可满足规则；每个声明阶段记录 executed/skipped/blocked/error、输入/输出及原因。跨批提升以已落盘且质量合格的 source-note 为基础，复用 finalizer，而非凭批次日期或 seed_terms 数量升格。seed 聚类结果可做候选发现，但来源支持与去重身份另外验证。

**回归风险：** 重建另一套全库状态导致 SSOT 分裂；以同词代替同主题；重命名/重复追加候选；升级后把已有人工专题覆盖。延续对象身份、revision 与 base hash 检查。

### 批次 F · 最后修存量，不清空索引、不按文件名猜版本
